1. 현재 저장소와 입력 확인
Git 작업 상태, 입력 경로, 활성 공통 계약, 참조 소스 identity, 실제 설치 도구를 확인해줘.
scripts/infrastructure_sources.py --check와 프레임워크 회귀 테스트를 실행해줘.
공통 JSON 계약 검사는 이전 single-exclusive 호환 범위다. 새 방향별 계약의 통과로 표시하지 마.
기존 infrastructure template·binding 검사는 이전 호환 방식의 검사다. 해당 방식을 재사용할 때
실행하고, 그 PASS를 새 native binding의 검증으로 표시하지 마.
통과·실패·건너뜀과 각 검증 범위를 보고해줘.
현재 작업에 필요한 설계별 검사는 해당 파일이 준비된 뒤 실행해줘.
소스와 evidence 해시가 다르면 어느 파일의 어떤 identity가 달라졌는지 기록해줘.
해시만 갱신하거나 검사를 약화해 PASS를 만들지 마. 재검증이 필요한 경계를 구분해줘.
이번 inspect_and_propose에서는 기존 소스·계약을 고치거나 HDL 구현을 시작하지 마.
사용자 변경과 기존 revision을 보존하고, 새 설계는 designs/<new_revision>/에 분리해줘.

2. 실제 모델 실행과 하드웨어 조사
모델 checkpoint의 정확한 commit, config·tokenizer·weight identity, 실행 라이브러리 버전,
실제로 호출되는 Python source와 attention/cache 구현을 확인하고 출처를 기록해줘.
로컬 snapshot을 먼저 확인하고 필요한 원격 정보는 공식 모델 저장소·공식 코드에서 확인해줘.
revision 미지정이면 확인 가능한 고정 commit을 후보로 제시하고 최종 선택 여부를 표시해줘.
지원하려는 prefill·decode를 실제로 실행하여 tensor shape/layout/dtype과 상태 변화를 추적해줘.
runtime_gemm_trace.py의 factory 방식은 관찰 도구다. GEMM 분류만으로 구현 가능을 선언하거나
NON_GEMM 영역을 생략하지 마. 실제 모델 source와 함께 모든 semantic operation을 식별해줘.
가중치 공유, bias, normalization, positional encoding, attention/mask, cache, FFN,
출력 head 등은 실제 모델에서 존재하는 연산만 포함해줘.
관찰하지 못한 경로와 지원하지 않을 경로를 분리하고, trace 1건을 전체 분기 증거로 쓰지 마.

하드웨어는 사용자가 지정한 스펙을 기준으로 조사해줘. config/hardware/zcu104.json의
존재를 사용자 선택으로 간주하지 마. 지정한 profile도 누락·오래된 값을 점검해줘.
보드·FPGA part, LUT/FF/DSP/BRAM/URAM, 클럭, PS/runtime, DDR 용량·합법 주소 범위,
AXI 폭·연결·대역폭, command BRAM, 도구 버전과 보드 실행 방식을 확인해줘.
측정값·스펙값·추정값을 구분하고 누락된 값은 미결정 또는 측정 필요로 표시해줘.
available_ps_ddr_ports는 사용 가능한 인터페이스 후보이며, 나열된 포트를 전부 연결하거나 사용하라는 뜻이 아니다.
이 모델에 실제 사용할 포트 조합, DataMover/channel 수, 트래픽 배분, interconnect와 대역폭·자원 비용을
제안하고 사용자와 논의한 뒤 확정해줘. 포트 수에 비례해 총 대역폭이 증가한다고 가정하지 마.
하드웨어 profile에 목표 클럭, Vivado 버전, board memory map 파일이 반드시 있어야 하는 것은 아니다.
목표 클럭은 workload와 구현 제약을 근거로 제안하고, 도구 버전은 실제 사용 가능한 환경을 확인해줘.
보드 실행 전에는 선택한 runtime의 링커 스크립트 또는 메모리 할당으로 합법 DDR 주소 범위를 확정해줘.
board_memory_map 파일을 필수로 요구하거나, 제공되지 않은 주소를 임의로 정하지 마.
현재 vendor IP가 해당 FPGA에 맞지 않으면 대체안과 비용을 제시하고 구현 가능을 단정하지 마.

3. 실행 범위와 수치·성능 후보 논의
먼저 모델·하드웨어 선택, 다음 실행 범위, 다음 수치·품질 목표 순으로 논의해줘.
실행 범위에는 batch, prefill 길이·chunk, decode 횟수, 최대 총 context,
padding/mask/position 지원, cache 정책, 출력 경계를 포함해줘.
성능 목표는 TTFT, decode token/s 또는 latency, 측정 workload와 포함 비용을 구체화해줘.
원래 모델 수치 형식과 양자화 후보의 정확도·메모리·DSP·전송 비용을 비교해줘.
가중치·activation·KV·중간값·누산·비선형 정밀도와 scale metadata 비용을 각각 다뤄줘.
실제 shape로 packed bytes, 온칩 bank·buffer 중복, KV 증가량, DDR 전송량과
계산량을 산정하고 배열 크기·tile·병렬도 후보가 자원·대역폭 목표에 맞는지 설명해줘.
누락된 항목을 한꺼번에 임의 확정하지 마. 다음 설계를 좌우하는 결정부터 질문하고
독립적인 조사·산정은 계속해줘. 답하지 않은 결정은 unresolved_decisions에 남겨줘.

4. 연산 → ISA → executor와 bank 후보 제안
각 semantic operation마다 입력·출력·상태, prefill/decode shape, ISA 명령열,
필요한 executor 또는 재사용 모드, bank와 DMA, PS/PL 책임을 표로 보여줘.
공유·fusion 후보의 수치 경계, buffer·port 비용, 검증 단위를 비교해줘.
모델 구조나 low-level Python 호출마다 opcode를 만들지 마.
GEMM 계열은 capability가 맞을 때 공유하고 embedding의 주소 선택과 tensor 계산을 구분해줘.
opcode와 module 목록은 후보로 제시하고 사용자와 논의한 뒤 확정해줘.
이 논의에서 designs/<new_revision>/structure_contract.json의 후보를 작성해줘.
동작 계약이 무엇을 할지 정하면 구조 계약은 어떤 모듈·연결·메모리·파이프라인으로 구현할지 정한다.
모듈별 책임·공유/인스턴스 수·실제 포트 연결·clock/reset·폭/주소 단위,
방향별 bank 역할·여러 포트의 Weight stripe 공급·executor 읽기/operand/core 경로,
buffer/credit·controller 예약/발행/완료/해제·END와 자원·대역폭 근거를 기록해줘.
구조 의무 ID를 요구사항·실제 출처·적용 모듈/연결·검사/기대 결과에 연결해줘.
ISA·bank·수치 계약과 활성 소스의 경로·버전·해시를 참조하고 고정 구조·허용한 조정 범위를 구분해줘.
inspect_and_propose에서는 후보와 영향받는 미결정 항목을 표시하고 합의·구현 완료로 꾸미지 마.

기본 transport는 PS-preloaded command BRAM이다. PS는 terminal END를 포함한
현재 프로그램 전체를 기록한 뒤 START를 publish하고 BUSY 동안 records를 수정하지 않는다.
dispatcher는 단일 PC의 현재 명령만 보고 막힌 PC를 건너뛰지 않는다.
선택한 활성 RTL과 합의한 계약을 기준으로 bank 획득·명령 수락 조건을 정해줘.
PC는 command valid/ready에서 진행하고 비충돌 명령의 동시 실행 여부를 명시해줘.
END는 새 발행을 중단하고 DONE은 필요한 완료 응답과 bank 해제 이후에 발생한다.
Command BRAM은 data-bank namespace와 분리하며 data bank 0은 합법이다.
새 설계는 읽기·쓰기 owner와 acquire/release/busy를 방향별로 분리해줘.
같은 방향에는 하나의 owner만 허용하고 입력은 읽기·출력은 쓰기 operand-port 역할로 예약해줘.
모든 필요한 방향별 역할을 원자적으로 예약·확인한 뒤 engine command를 제시해줘.
반대 방향의 동시 실행은 실제 memory 충돌 정책과 read_addr < commit 범위가 허용할 때만 가능하다.
새 generation·append·in-place input 보존과 실제 획득·해제 cycle은 docs/framework_workflow.md 1.5절을 따라줘.
현재 single-exclusive primitive와 예전 JSON 계약을 방향별 구현으로 간주하지 마.
참조 명령 header는 opcode + SRC0~SRC3 + DST + 연산별 payload이며,
bank ID 폭은 이번 bank 구성에서 구한다. Engine payload는 모델별로 정한다.
쓰기 중 읽기를 겹치려면 engine의 committed prefix·데이터 준비 조건을 별도로 정의한다.
방향별 ownership만으로 데이터가 준비됐다고 판단하지 마.
busy/owner와 tensor valid·progress·논리 lifetime은 다른 상태로 명세해줘.
실패한 command는 destination을 유효하게 commit하지 않는다.
Compute의 tensor operand는 논리 bank ID다. DDR 주소·local raw address·bank offset을 전달하지 마.
DDR residency 타일링은 PS, local bank 안의 계산 타일링은 합의한 executor가 담당한다.

END 외의 FENCE, bank lifetime flag/control, LOOP/JUMP, 복합 명령의 필요성은
실제 dependency와 명령 수로 검토해줘. 다른 bank를 통한 DDR STORE→LOAD 의존성처럼
bank scoreboard만으로 표현되지 않는 순서도 조사해줘.
기존 SmolLM2의 GEMM_TILES 등 dispatcher 내부 DMA 확장을 기본값으로 복사하지 마.
순수 DMA/compute 명령열과 비교하고 PS scheduling·주소 경계·response identity에 대한
영향 및 공통 계약·검사기와의 충돌을 설명한 뒤 사용자와 결정해줘.

5. 명령 용량과 조각별 실행
instruction record 크기와 END·control을 포함한 prefill/decode별 명령 수를 계산해줘.
한 command BRAM에 들어가지 않으면 단일 BRAM의 조각별 실행을 먼저 비교해줘.
각 조각은 END로 drain한다. DONE은 조각 완료이며 전체 모델 완료와 구분해줘.
조각 사이 bank 데이터·valid/progress·KV/DDR 상태의 유지, PC 재시작과 reset 범위,
PS의 DONE/오류 확인→다음 records 적재→END→START 절차를 명시해줘.
command capacity, 조각 경계, PS 적재·시작 비용과 예상 전체 지연을 산정해줘.
더블 버퍼링·LOOP/JUMP는 단일 BRAM 방식 대비 필요성과 추가 자원·제어·검증 비용을
제시한 뒤 사용자와 결정해줘. 근거 없이 command ring queue를 도입하지 마.

6. 합의 후 reference와 ISA interpreter 검증
합의된 trace, ISA, bank layout에 schema와 제어 방식의 버전을 명시해 저장해줘.
현재 구현 범위의 구조 계약도 구체화하고 동작·ISA·bank 계약과의 정합성을 확인해줘.
기존 공통 검사기의 PASS는 새 구조 계약 적합성 검사가 아니다. 설계별 검사와 실제 검증 범위를 명시해줘.
scripts/check_isa_design.py는 현재 단일 exclusive ownership을 요구한다. 새 native 방향별
ownership을 사용하는 설계는 ISA·binding schema를 정의하고 검증한 뒤 검사 통과를 표시해줘.
새 의미를 이전 호환 schema에 억지로 맞추거나 PASS를 위해 검사를 약화하지 마.
후보 상태를 reviewed/frozen/passed로 허위 표시하거나 미구현 모듈의 빈 계약을 만들지 마.
Python ISA interpreter는 실제 tensor 값·cache·bank 상태를 실행해야 한다.
명령별 golden 입력·출력·중간 상태와 완전한 tensor 또는 재생 가능한 파일·hash를 기록해줘.
reference와의 semantic 경계 비교, 합의한 하드웨어 arithmetic oracle과의 비교를 구분해줘.
scale·zero point·누산 폭/순서·rounding·saturation·비선형 근사·nonfinite 규칙을 명시해줘.
prefill과 이어지는 decode, 여러 decode, 조각 경계, tail, 최대 지원 길이·cache 경계를
검증해줘. 구조/주소 경계만 확인했다면 해당 길이의 수치 검증이라고 표시하지 마.
tensor 오차·logits·토큰/품질 기준은 사용자가 합의한 기준으로 판단해줘.
interpreter 검증 실패나 구현에 영향을 주는 미결정 사항이 있으면 관련 HDL을 시작하지 마.

7. 합의한 모듈의 증분 구현과 검증
현재 executor마다 연산 범위·알고리즘·포트·bank 접근·수치 규칙·병렬도·목표 클럭/자원과
golden 검증 기준을 먼저 제안하고 사용자 결정으로 module contract를 작성해줘.
먼저 동작·ISA·bank 계약과 구조 계약을 읽고 현재 모듈의 구현 방식을 도출해줘.
현재 구조 의무를 구체화하고 module packet에 구조 계약 경로·버전·해시·적용 의무 ID를 참조해줘.
의무별 구현 파일·인스턴스·포트·parameter·cycle·검사를 대응시킨 뒤 RTL을 작성해줘.
허용 범위 안의 선택은 구체적인 설정으로 기록하고, 고정 경계 변경은 근거·영향 범위와 새 계약 버전을 남겨 재검증해줘.
이미 승인한 결정을 재승인받거나 별도 계약 승인 계층을 만들지 마.
Parent는 모델·ISA·bank·작업 분해를 담당하고, 구현 Child와 별도 독립 검증 Child를 사용해줘.
과거 스킬을 사용하지 않고 현행 계약과 같은 구조 계약·구현 대응표·해당 모듈 계약을 각 Child의 기준으로 전달해줘.
독립 검증 Child는 실제 RTL의 구성·연결과 전체 동작을 구조 의무에 대조해줘. 파일 존재만으로 통과시키지 마.
각 executor의 bank 읽기는 요청 발행 → 응답 정렬 → operand register → 계산 core로 파이프라이닝해줘.
Bank 출력을 계산 core에 직접 조합 연결하지 마. Weight·activation·scale·KV의 데이터와
valid·last·mask·index·transaction metadata를 실제 읽기 지연에 맞춰 정렬해줘.
utils/pipeline.sv는 고정 지연 정렬용이며 stall 기능이 없으니 backpressure는 응답 버퍼·credit으로 처리해줘.
남은 읽기·operand·계산 파이프라인과 최종 쓰기가 끝난 뒤 완료·bank 해제를 허용해줘.
구체적인 연결·cycle·검증 기준은 docs/framework_workflow.md 1.4절을 따라줘.
각 연산 engine의 명령 수락·context 저장·bank/core 실행·memory drain·식별 가능한
완료/오류 응답·bank 해제 조건을 해당 계약에 명시해줘.
선택한 활성 infrastructure 파일과 기록한 재사용·수정 결정을 구현 입력으로 사용해줘.
실제 파일 경로·해시·인터페이스·의존성을 구현·검증 Agent에 전달해줘.
모델별 opcode·port routing·payload·수치 규칙은 새 revision에서 정하고
미구현·미연결 연산은 거부해야 한다. 필요한 FIFO와 버퍼링을 검증해줘.
별도 범용 executor·ownership/router·adapter·command queue 계층을 선행 과제로 만들지 마.
새 revision의 계약으로 binding·생성 RTL을 검증해줘. 소스 identity·컴파일/elaboration이나
이전 fixture PASS는 새 모델 수치·합성·timing·보드 증거가 아니다.
삭제한 template의 USER 영역을 채우는 절차를 필수 작성 방식으로 요구하지 마.
golden 비교, RTL simulation/lint, 합성, routed timing/resource, 통합, 실물 보드를 구분해줘.
사용자의 누적 보드 checkpoint 결과가 수용되면 다음 executor로 진행해줘.
이 대화에서 해당 결정과 단계 진행을 이미 승인했다면 같은 승인을 반복 요청하지 마.

8. 보드 인계와 완료 판정
같은 build의 BIT/HWH/XSA 및 선택한 runtime의 앱·모델 asset·실행 절차를 준비하고
source·contract·vector·artifact·사용자 결과 identity를 연결해줘.
실물 FPGA는 사용자가 실행한다. 기대 값·오차 한계·성능 측정·진단 방법을 제공해줘.
명령 실행 완료, 일부 tensor/sample 통과, 전체 수치·품질 통과, 성능 목표 달성을 구분해줘.
보드에서 합의한 prefill/decode 범위와 결과를 검증하기 전에는 전체 모델 가속 완료로 쓰지 마.
