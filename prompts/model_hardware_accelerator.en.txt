The default transport is PS-preloaded command BRAM. PS writes the entire current program including terminal END,
then publishes START; records cannot be modified while BUSY.
The dispatcher examines only the current instruction at a single PC and never skips a blocked PC.
Define bank acquisition and command acceptance from the selected active RTL and the agreed design contract.
Advance the PC on command valid/ready. Specify whether nonconflicting commands may remain outstanding.
END stops new issue; DONE waits for required completions and bank releases.
Command BRAM is separate from the data-bank namespace; data bank 0 is legal.
New designs separate read/write owners and acquire/release/busy per direction.
Allow one owner per direction; reserve input read roles and output write operand-port roles.
Atomically reserve and confirm all required directional roles before presenting the engine command.
Overlap requires the actual memory conflict policy and the read_addr < commit availability bound.
Follow section 1.5 of docs/framework_workflow.md for generation, append, in-place input preservation and ownership cycles.
Do not treat existing single-exclusive primitives or previous JSON contracts as directional implementations.
The reference command header is opcode + SRC0..SRC3 + DST + opcode-specific payload; derive bank-ID
width from this design's bank inventory. Engine payloads remain model-specific.
Read-while-write overlap requires an explicit committed-prefix/data-availability policy in the engine;
split ownership alone does not establish that the data is ready.
Specify busy/owner separately from tensor validity, progress, and logical lifetime.
Failed commands do not commit a valid destination.
Compute tensor operands are logical bank IDs: do not pass DDR addresses, raw local addresses, or bank offsets.
PS owns DDR residency tiling; the agreed executor owns computation tiling within local banks.

Assess whether FENCE, bank lifetime flags/control, LOOP/JUMP, or compound commands beyond END are needed
using actual dependencies and command counts. Investigate ordering not captured by bank scoreboarding,
including DDR STORE→LOAD dependencies through different banks.
Do not copy dispatcher-internal DMA expansions such as the existing SmolLM2 GEMM_TILES as defaults.
Compare them with explicit DMA/compute sequences; explain effects on PS scheduling, address boundaries,
response identity, and conflicts with common contracts/checkers before deciding with the user.

5. Assess command capacity and chunk execution
Compute instruction record size and prefill/decode command counts including END and control records.
If the program cannot fit in one command BRAM, evaluate execution in chunks using a single BRAM first.
Each chunk drains through END. DONE means chunk completion, not full-model completion.
Specify preservation of bank data/validity/progress and KV/DDR state between chunks, PC restart and reset scope,
and the PS sequence: check DONE/errors → write the next records → END → START.
Estimate command capacity, chunk boundaries, PS loading/start costs, and total latency.
Compare double buffering and LOOP/JUMP with the single-BRAM approach in necessity, resources, control, and verification costs,
then decide with the user. Do not introduce a command ring queue without justification.
